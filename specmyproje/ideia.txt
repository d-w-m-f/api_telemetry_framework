Papo Gemini:

A estruturação dos seus dois Bounded Contexts deve refletir os padrões arquiteturais que melhor resolvem os problemas específicos de cada um: Layered Architecture para orquestrar o fluxo sequencial do laboratório e uma abordagem orientada a interfaces (Ports and Adapters) nas fixtures para garantir a troca rápida da DB-Engine.

Aqui está a proposta de módulos e pastas para você estruturar suas especificações:

1. Bounded Context: O Laboratório (Core Domain)
Como este contexto é o cérebro da operação, a modelagem segue estritamente a Arquitetura em Camadas (Layered Architecture). A divisão modular reflete o fluxo de cima para baixo.

Módulo de Domínio (domain/)

Responsabilidade: O núcleo matemático e lógico. Não importa nada e não depende de bibliotecas externas.

Componentes:

Experiment: Entidade que representa a rodada atual.

LoadMatrix: Objeto de valor (Value Object) que cruza e valida os eixos (Linguagem vs. Carga vs. DB).

Analytics: Serviços de domínio que calculam percentis (P95, P99), variância e decidem se o teste é válido.

Módulo de Aplicação (application/)

Responsabilidade: Orquestrar o fluxo de trabalho. É o "maestro" que dita a ordem das coisas.

Componentes:

ExperimentRunner: Recebe a spec, manda a infraestrutura subir os recursos, aciona o gerador de carga, manda coletar métricas e passa os dados para o Analytics.

Módulo de Infraestrutura (infrastructure/)

Responsabilidade: Sujar as mãos com o mundo externo, redes e orquestradores. Implementa as interfaces definidas pela Aplicação.

Componentes:

Provisioner: Conecta-se à API do Docker ou aos manifests de um cluster self-hosted (como um K3s em servidor dedicado) para alocar os recursos físicos (CPU/Memória).

StressGenerator: Integração com a ferramenta de geração de carga (os scripts em bench/scenarios/).

TelemetryCollector: Integração que consome os dados do Prometheus ou logs brutos durante a execução.

2. Bounded Context: APIs Fixture (Subdomínio de Suporte)
Este contexto é a massa de manobra. A modelagem aqui foca no desacoplamento da camada de dados para permitir o easy-swap dos eixos (Postgres, Redis, etc.), mantendo a lógica de negócio intencionalmente anêmica.

Módulo de Catálogo e Pedidos (core/ ou domain/)

Responsabilidade: Rotas HTTP e a lógica mínima para responder às requisições do laboratório de forma uniforme.

Componentes:

Serviços de CRUD básicos.

As Portas: Interfaces como IPedidoRepository e ICatalogoRepository.

Módulo de Adaptadores / Infraestrutura (adapters/)

Responsabilidade: Implementar os contratos de banco de dados e os middlewares de observabilidade injetados dinamicamente pelos eixos.

Componentes:

PostgresEngine: Implementa as interfaces usando SQL.

CachedRedisEngine: Implementa a estratégia com cache.

TelemetryMiddleware: Liga/desliga os traces (1% ou 100%) conforme a variável de ambiente injetada pelo Laboratório.

Essa estrutura isola perfeitamente a inteligência (o laboratório) da massa de teste (a fixture), garantindo que você possa refatorar seus scripts de orquestração Python ou Go sem quebrar os limites dos contratos.

Como você prefere documentar as especificações de injeção de dependência que o Orquestrador vai usar para plugar o adaptador correto na Fixture em tempo de execução?
